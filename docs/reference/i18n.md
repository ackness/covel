# Internationalization

Covel 面向用户的多语言字段统一使用 `I18nText`：

```ts
type I18nText = string | Record<string, string>;
```

locale key 支持 `Intl.getCanonicalLocales()` 可 canonicalize、且适合安全文件名的 Unicode locale identifier，例如 `ru`、`ru-RU`、`sr-Latn`、`zh-Hant-TW` 与 `en-u-ca-gregory`。private-use / grandfathered BCP 47 tag（例如 `x-elvish`、`i-klingon`）不属于该持久化与文件变体契约。面向用户的自然语言文本应提供目标语言和 English fallback；中文不再是必需项。稳定 ID、路径、URL、图标名和状态值不做翻译。

## 内置语言与扩展边界

当前仓库随包发布 `zh-CN`、`en-US` 与 `ru-RU`。Web 的活动 locale registry 由 `apps/web/src/i18n/locales/*.json` 自动发现：文件名是 canonical locale code，设置校验与选项、浏览器检测、切换器、i18next resources 都从扫描结果派生。新增完整 catalog 不再修改 TypeScript registry 或组件。

`@covel/shared` 的 `LocaleDefinition` / `defineLocaleRegistry()` 仍提供框架默认值、fallback 与宿主组合入口。Web 会为非内置 catalog 通过 `Intl.DisplayNames` 自动生成各界面语言下的名称，以主语言大写形式生成短标签，并使用 English fallback。Catalog 使用动态 import，只有当前语言及其 fallback 会被加载，不会把所有贡献词典塞进入口 bundle。

该自动发现是构建时能力：把 JSON 放入仓库或发行包后重新构建即可。运行时安装的 community plugin 不会在浏览器或 Electron main process 中执行代码，因此不能覆盖已经构建的 core UI catalog；插件/世界内容可使用同一套安全、可 canonicalize 的 locale identifier。Desktop Web 界面会使用新 catalog，未内置该语言的 Electron 原生菜单与启动错误会安全回退 English。

UI catalog 与 LLM prompt 是两套独立资源。新增 JSON 只翻译 Web 界面，不会把英文或中文 prompt 机器翻译成目标语言：

- 框架外置 prompt 使用 `prompts/server/<name>.<locale>.md` 或 script 兼容的主语言短键文件，例如 `compactor.ru-RU.md` / `compactor.ru.md`、`generate-world.ru-RU.md`。缺失时使用 English 模板，再回退 canonical 文件；English 模板仍会明确要求模型以当前 session locale 输出自然语言。
- Agent 插件在 runtime 的 `PLUGIN.md` 同目录加入 `PLUGIN.ru-RU.md` / `PLUGIN.ru.md`。目标语言缺失时先尝试 `PLUGIN.en-US.md` / `PLUGIN.en.md`，最后才使用 canonical `PLUGIN.md`；结构契约始终取 canonical manifest。
- 世界叙事 prompt 使用 `WORLD.ru-RU.md` / `WORLD.ru.md`，缺失时使用世界的 canonical `WORLD.md`。
- 高级部署可以用 `COVEL_PROMPTS_DIR` 指向一套自维护的框架 prompt 根目录。它替换整个 prompt root，因此必须保留应用实际使用的 canonical 文件。

运行时插件可以携带和修改自己的 prompt，但不能覆盖 core framework prompt；覆盖核心 prompt 需要在源码/发行包中加入文件，或由部署者显式配置 `COVEL_PROMPTS_DIR`。

## 统一解析规则

所有框架和 Web UI 显示都必须通过 `@covel/shared` 的 `resolveI18nText(value, locale)` 解析，不得在组件内另写 `startsWith("en")`、`split("-")` 或 `Object.values()[0]` 式语言判断。解析顺序是：

1. 当前 locale 精确匹配，忽略大小写并兼容 `_` / `-`，例如 `en_US` 可匹配 `en-US`。
2. 当前主语言的短键，再尝试同语言、同 script 的其他区域键，例如 `en-US` 匹配 `en`；script 不同不会互相回退，例如 `zh-Hant` 不匹配 `zh` / `zh-CN`。
3. 按 locale registry 中声明的 `fallbackLocales` 依次回退；内置 registry 的最终 fallback 是 English。
4. 对象中第一个可用字符串。

没有传入 locale 时，为保持服务端和旧数据的确定性，直接取对象中第一个可用字符串。Web 组件应总是传当前 `i18n.language`。

`localeLanguage(locale)` 只负责提取主语言。资源候选必须使用 `localeLookupCandidates()`，同语言兼容性必须使用 `localesShareLanguageAndScript()` 或 registry 的 `match()`，不得仅凭主语言跨 script 折叠。

世界维度等任意嵌套数据统一通过 `resolveI18nDeep(value, locale)` 解析。它只负责递归遍历数组和普通对象；遇到 locale map 时仍委托 `resolveI18nText`，因此与 UI 使用完全相同的精确匹配、同语言匹配和英文回退规则。

## Web 边界

API 或插件 JSON 属于不可信输入。Web UI 通过 `apps/web/src/lib/i18n-text.ts` 的 `resolveDisplayText` 先丢弃非字符串字段，再调用共享 resolver，避免嵌套对象被当作 React child 渲染。已有的 `resolveI18n`、`text` 和 `textValue` 只是兼容入口，它们也必须委托到这条统一链路。

## 新增一种语言

以下以日语 `ja-JP`（文件变体可使用 exact `ja-JP` 或 script 兼容的短键 `ja`）为例。只翻译一个世界包时无需复制应用 catalog；要让玩家直接选择 `ja-JP`，只需随 Web/发行包加入完整 JSON catalog。

### 1. 注册应用语言

1. 运行 `pnpm i18n:add ja-JP` 生成完整模板，也可以手动复制 `apps/web/src/i18n/locales/en-US.json` 为 `apps/web/src/i18n/locales/ja-JP.json`。脚手架会按目标语言的 `Intl.PluralRules` 自动补齐 English 已标记 plural base 所需的 category。文件名必须是安全 canonical BCP 47 locale，且不能复用内置 code/alias（如 `zh`、`zh-Hans`、`en`、`ru`）；无需修改 `i18n/index.ts`、设置 schema 或切换器。
2. 只翻译 value，保持所有基础 key、JSON 类型、数组长度和 `{{ interpolation }}` token 不变。任何包含 `{{count}}` 的基础文案都可以增加目标语言需要的 i18next plural key，例如俄语的 `_few` / `_many`；脚手架生成的 category 只是 English 占位值，必须一并翻译。
3. 运行 `pnpm check:i18n`。检查器会校验文件名、内置 alias 冲突、与 `en-US` 的基础结构、English 已标记 plural base 的目标语言 categories、所有 plural variant 的插值变量以及代码实际使用的 key。
4. 运行 `pnpm --filter @covel/web test` 和 `pnpm --filter @covel/web build`。构建后 `ja-JP` 会自动出现在设置、顶栏和 Onboarding 中；`ja` / `ja-JP` 浏览器 locale 会自动匹配。
5. 可选：增加 `<name>.ja-JP.md` / `<name>.ja.md` framework prompt、`PLUGIN.ja-JP.md` / `PLUGIN.ja.md`、`WORLD.ja-JP.md` / `WORLD.ja.md` 或 Electron 原生菜单翻译；缺少时按上文规则回退，不影响 Web UI catalog 生效。

无法立即翻译的框架内容必须明确回退到 English，而不是回退中文或改变稳定字段、枚举和业务契约。

### 2. 本地化插件

短标签、说明和 UI spec 使用 locale map：

```yaml
displayName:
  zh: 骰子判定
  en: Dice Check
  ja: ダイス判定
```

Agent runtime 的长提示词使用同目录下的 `PLUGIN.ja-JP.md` 或 `PLUGIN.ja.md`。语言变体只写翻译后的正文和必要的自然语言 frontmatter；`stage`、`trigger`、`capabilities`、`tools`、`input.inject`、schema 与超时等结构字段继续从 canonical `PLUGIN.md` 继承。目标语言文件缺失时会先尝试 English 变体，再回退 canonical 文件。Function runtime 或 hook 生成的通知与 prompt 应根据 `ctx.locale` / hook payload 的 `locale` 解析，不能只写死某一种语言。完整约束见[插件作者指南](../guide/plugin-authoring.md#运行时文案的-i18n重要)。

### 3. 本地化世界包

先在 `world.yaml` 声明可用语言，并为短字段提供翻译：

```yaml
defaultLocale: en-US
supportedLocales:
  - en-US
  - ja-JP
name:
  en: My World
  ja: 私の世界
summary:
  en: An example world.
  ja: サンプル世界です。
```

保留默认内容的 canonical 路径，再按 exact locale 或 script 兼容的主语言短键添加变体：

```text
worlds/my-world/
├── WORLD.md
├── WORLD.ja.md
├── characters/
│   ├── main-cast.json
│   └── main-cast.ja.json
└── data/rules/
    ├── core.yaml
    └── core.ja.yaml
```

`data/world.data.yaml` 继续声明 canonical source，例如 `characters/main-cast.json`。创建 `ja-JP` 会话时，WorldData loader 依次尝试同目录的 `main-cast.ja-JP.json`、`main-cast.ja.json`，再回退到声明的 `main-cast.json`；YAML、JSON、Markdown、text 和 media source 都使用同一规则。`WORLD.md` 同样按 exact locale → script 兼容主语言 → canonical 文件解析。这样可以逐步翻译，无需为了加入一种语言复制整个世界包。更多 source 规则见 [WorldData 的 Locale 变体解析](./world-data.md#locale-变体解析namelocaleext)。

### 4. 校验

```bash
pnpm check:i18n
pnpm --filter @covel/shared test -- i18n
pnpm --filter @covel/tools test -- world-dimension-tools
pnpm --filter @covel/web test -- i18n-text execution-timeline
```

还应实际切换到新 locale，检查设置页、世界选择页、会话创建、插件面板、Agent prompt 和 WorldData 导入结果。`pnpm check:i18n` 负责发现现有扫描范围内的裸 CJK 文案、缺少 English fallback 的 `I18nText`，以及任一 Web catalog 缺 key 的问题，但不会验证翻译质量。

## 插件示例

```yaml
name: dice-check
displayName:
  zh: 骰子判定
  en: Dice Check
description:
  zh: 为有失败风险的行动提供骰子判定。
  en: Resolves risky actions with dice checks.
```

`name` 是稳定的插件 ID；插件列表、设置导航和执行时间线都显示经当前 locale 解析后的 `displayName`，只在缺失时回退到 `name` / plugin ID。
