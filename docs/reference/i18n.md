# Internationalization

Covel 面向用户的多语言字段统一使用 `I18nText`：

```ts
type I18nText = string | Record<string, string>;
```

推荐使用短语言键 `zh` + `en`，也支持 `zh-CN`、`zh-TW`、`en-US`、`en-GB` 等区域键。面向用户的自然语言文本应同时提供中英文；稳定 ID、路径、URL、图标名和状态值不做翻译。

## 内置语言与扩展边界

当前应用界面内置 `zh-CN` 与 `en-US`。世界包和插件的数据格式不把语言限制在这两种：作者可以声明其他 BCP 47 locale，并提供对应的 `I18nText` 和文件变体。不过，要让原版 Web / Desktop 界面能够选择第三种语言，还需要按下文扩展应用的 locale 注册、设置项和界面词典；只添加世界包文件不会自动在语言切换器里出现新选项。

## 统一解析规则

所有框架和 Web UI 显示都必须通过 `@covel/shared` 的 `resolveI18nText(value, locale)` 解析，不得在组件内另写 `startsWith("en")`、`split("-")` 或 `Object.values()[0]` 式语言判断。解析顺序是：

1. 当前 locale 精确匹配，忽略大小写并兼容 `_` / `-`，例如 `en_US` 可匹配 `en-US`。
2. 当前主语言的短键，再尝试同语言的其他区域键，例如 `en-US` 匹配 `en`。
3. 英文回退：`en-US` → `en` → 其他英文区域键。
4. 对象中第一个可用字符串。

没有传入 locale 时，为保持服务端和旧数据的确定性，直接取对象中第一个可用字符串。Web 组件应总是传当前 `i18n.language`。

`localeLanguage(locale)` 是唯一的主语言标准化方法，用于语言分组、世界包排序和浏览器语言检测。

世界维度等任意嵌套数据统一通过 `resolveI18nDeep(value, locale)` 解析。它只负责递归遍历数组和普通对象；遇到 locale map 时仍委托 `resolveI18nText`，因此与 UI 使用完全相同的精确匹配、同语言匹配和英文回退规则。

## Web 边界

API 或插件 JSON 属于不可信输入。Web UI 通过 `apps/web/src/lib/i18n-text.ts` 的 `resolveDisplayText` 先丢弃非字符串字段，再调用共享 resolver，避免嵌套对象被当作 React child 渲染。已有的 `resolveI18n`、`text` 和 `textValue` 只是兼容入口，它们也必须委托到这条统一链路。

## 新增一种语言

以下以日语 `ja-JP`（文件变体使用主语言短键 `ja`）为例。可以只完成所需层级：只翻译一个世界包时，无需复制整套应用界面；要让玩家在原版客户端中直接选择 `ja-JP`，则需要同时完成应用层。

### 1. 注册应用语言

1. 以 `apps/web/src/i18n/locales/en-US.json` 的完整 key 集为模板，新增 `apps/web/src/i18n/locales/ja-JP.json`。
2. 在 `apps/web/src/i18n/index.ts` 中导入词典，加入 `resources` 与 `supportedLngs`。
3. 在 `apps/web/src/i18n/locale-detector.ts` 中扩展 `SupportedLocale`，并按需加入浏览器语言检测。
4. 在 `apps/web/src/settings/registry/core.ts` 中扩展 `ui.locale` 的 schema 与选项。同步检查 `apps/web/src/routes/__root.tsx` 等目前假设中英双向切换的入口。
5. 若分发 Desktop 应用，同步扩展 `apps/desktop/src/main-i18n.ts` 的 locale 类型、检测和桌面端文案。

应用中仍有少量只提供中英模板的专用逻辑。新增 locale 时应搜索 `"zh-CN" | "en-US"`、`z.enum(["zh-CN", "en-US"])` 和显式的中英分支；无法立即翻译的内容应明确回退到英文，而不是改变稳定字段或业务契约。

### 2. 本地化插件

短标签、说明和 UI spec 使用 locale map：

```yaml
displayName:
  zh: 骰子判定
  en: Dice Check
  ja: ダイス判定
```

Agent runtime 的长提示词使用同目录下的 `PLUGIN.ja.md`。语言变体只写翻译后的正文和必要的自然语言 frontmatter；`stage`、`trigger`、`capabilities`、`tools`、`input.inject`、schema 与超时等结构字段继续从 canonical `PLUGIN.md` 继承。Function runtime 或 hook 生成的通知与 prompt 应根据 `ctx.locale` / hook payload 的 `locale` 解析，不能只写死某一种语言。完整约束见[插件作者指南](../guide/plugin-authoring.md#运行时文案的-i18n重要)。

### 3. 本地化世界包

先在 `world.yaml` 声明可用语言，并为短字段提供翻译：

```yaml
defaultLocale: en-US
supportedLocales:
  - en-US
  - ja-JP
name:
  en: My World
  ja: 私の世界
summary:
  en: An example world.
  ja: サンプル世界です。
```

保留默认内容的 canonical 路径，再按主语言短键添加变体：

```text
worlds/my-world/
├── WORLD.md
├── WORLD.ja.md
├── characters/
│   ├── main-cast.json
│   └── main-cast.ja.json
└── data/rules/
    ├── core.yaml
    └── core.ja.yaml
```

`data/world.data.yaml` 继续声明 canonical source，例如 `characters/main-cast.json`。创建 `ja-JP` 会话时，WorldData loader 会先尝试同目录的 `main-cast.ja.json`，不存在时回退到声明的 `main-cast.json`；YAML、JSON、Markdown、text 和 media source 都使用同一规则。`WORLD.md` 同样按 `WORLD.<lang>.md` → `WORLD.md` 解析。这样可以逐步翻译，无需为了加入一种语言复制整个世界包。更多 source 规则见 [WorldData 的 Locale 变体解析](./world-data.md#locale-变体解析namelangext)。

### 4. 校验

```bash
pnpm check:i18n
pnpm --filter @covel/shared test -- i18n
pnpm --filter @covel/tools test -- world-dimension-tools
pnpm --filter @covel/web test -- i18n-text execution-timeline
```

还应实际切换到新 locale，检查设置页、世界选择页、会话创建、插件面板、Agent prompt 和 WorldData 导入结果。`pnpm check:i18n` 负责发现现有扫描范围内的裸 CJK 文案与插件翻译问题，但不会证明一种新语言已经覆盖全部界面 key。

## 插件示例

```yaml
name: dice-check
displayName:
  zh: 骰子判定
  en: Dice Check
description:
  zh: 为有失败风险的行动提供骰子判定。
  en: Resolves risky actions with dice checks.
```

`name` 是稳定的插件 ID；插件列表、设置导航和执行时间线都显示经当前 locale 解析后的 `displayName`，只在缺失时回退到 `name` / plugin ID。
