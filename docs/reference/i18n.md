# Internationalization

Covel 面向用户的多语言字段统一使用 `I18nText`：

```ts
type I18nText = string | Record<string, string>;
```

locale key 支持 `Intl.getCanonicalLocales()` 可 canonicalize、且适合安全文件名的 Unicode locale identifier，例如 `ru`、`ru-RU`、`sr-Latn`、`zh-Hant-TW` 与 `en-u-ca-gregory`。private-use / grandfathered BCP 47 tag（例如 `x-elvish`、`i-klingon`）不属于该持久化与文件变体契约。面向用户的自然语言文本应提供目标语言和 English fallback；中文不再是必需项。稳定 ID、路径、URL、图标名和状态值不做翻译。

## 内置语言与扩展边界

当前仓库随包发布 `zh-CN`、`en-US` 与 `ru-RU`。Web 的活动 locale registry 由 `apps/web/src/i18n/locales/*.json` 自动发现：文件名是 canonical locale code，设置校验与选项、浏览器检测、切换器、i18next resources 都从扫描结果派生。新增完整 catalog 不再修改 TypeScript registry 或组件。

`@covel/shared` 的 `LocaleDefinition` / `defineLocaleRegistry()` 仍提供框架默认值、fallback 与宿主组合入口。Web 会为非内置 catalog 通过 `Intl.DisplayNames` 自动生成各界面语言下的名称，以主语言大写形式生成短标签，并使用 English fallback。Catalog 使用动态 import，只有当前语言及其 fallback 会被加载，不会把所有贡献词典塞进入口 bundle。

该自动发现是构建时能力：把 JSON 放入仓库或发行包后重新构建即可。运行时安装的 community plugin 不会在浏览器或 Electron main process 中执行代码，因此不能覆盖已经构建的 core UI catalog；插件/世界内容可使用同一套安全、可 canonicalize 的 locale identifier。Desktop Web 界面会使用新 catalog，未内置该语言的 Electron 原生菜单与启动错误会安全回退 English。

UI catalog 与 LLM prompt 是两套独立资源。新增 JSON 只翻译 Web 界面，不会把英文或中文 prompt 机器翻译成目标语言：

- 框架外置 prompt 使用 `prompts/server/<name>.<locale>.md` 或 script 兼容的主语言短键文件，例如 `generate-world.ru-RU.md` / `generate-world.ru.md`。缺失时使用 English 模板，再回退 canonical 文件；English 模板仍会明确要求模型以当前 session locale 输出自然语言。
- 插件提示词正文与固定提示段是**指令**，不是玩家看到的内容。canonical `PLUGIN.md` / `RUNTIME.md` 的正文必须是 English；只有简体中文有变体文件：`PLUGIN.zh.md` / `RUNTIME.zh.md`（也可用 `zh-CN`、`zh-Hans` 等更精确的文件名）。简体中文会话（`zh`、`zh-CN`、`zh-Hans`）读取中文变体，其余语言（包括 `ru-RU` 和繁体中文 `zh-Hant` / `zh-TW`）一律读取 English canonical，模型仍按会话 locale 输出玩家可见文本。繁体会话不读简体指令，因为简体指令会把输出带向简体字。`PLUGIN.ru.md` 之类的文件不会被读取：加载器记录警告，`pnpm check:prompts` 报错。
- 中文变体只需声明正文和 `contributes.prompt` 的 `content`；frontmatter 可以为空（`---` 紧跟 `---`）。省略的字段从 canonical 继承，结构契约始终取 canonical manifest。清单的 `displayName/description/label` 是玩家可见标签，canonical 文件写 English，译文放在 `locales/<locale>.yaml`，不放进提示词变体文件。
- 中文变体是英文的翻译，两者必须提到同一组工具名、注入块标签和 `runtime-inputs.<name>`。`plugins/prompt-variants.lock.json` 记录每一对的内容指纹：只改英文不改中文会让 `pnpm check:prompts` 失败；两边都改完后运行 `pnpm prompts:lock` 重新记录。
- 内置插件必须中英双份：凡是模型会读取的提示词（agent runtime 的正文、`contributes.prompt` 固定段）都要有中文变体，`pnpm check:prompts` 强制这一点。function runtime 的正文只是给作者看的说明，只写 English。社区插件只需要 English。
- `templates/` 里的插件模板受同样的规则约束（English 正文、不允许其他语言的变体文件），但不带中文变体：用 `pnpm create-plugin` 生成的插件从 English 开始，标签的中文在 `locales/zh.yaml`。
- 框架自己拼进提示词的指令句（前置段的运行框架、输出语言规则和完成约定，纠错提示，开场 user 消息）遵循同一规则，整段前置段只用一种语言，由 `@covel/shared` 的 `instructionLocaleFor()` 决定用中文还是 English。代码拼进提示词的其他固定文字（数据块的标题和说明、截断与裁剪标记、重试提示）也是指令，规则见[代码拼进提示词的文字](#代码拼进提示词的文字)。
- `COVEL_INSTRUCTION_LOCALE=en|zh` 强制所有会话使用同一种指令语言，用于对比两种语言的效果，或在某个模型明显更适合其中一种时固定下来。它不改变会话的内容语言。
- 世界叙事 prompt 使用 `WORLD.ru-RU.md` / `WORLD.ru.md`，缺失时使用世界的 canonical `WORLD.md`。
- 高级部署可以用 `COVEL_PROMPTS_DIR` 指向一套自维护的框架 prompt 根目录。它替换整个 prompt root，因此必须保留应用实际使用的 canonical 文件。

运行时插件可以携带和修改自己的 prompt，但不能覆盖 core framework prompt；覆盖核心 prompt 需要在源码/发行包中加入文件，或由部署者显式配置 `COVEL_PROMPTS_DIR`。

### 代码拼进提示词的文字

提示词正文之外，框架和插件的代码还会往提示词里写固定的文字：一个数据块前后的说明句、一个标题、一条纠错或重试提示。简体中文会话的正文是中文，这些文字是 English 时，同一段提示词就换了语言，小模型最容易在这里把输出写成 English。每一处按它是什么来处理：

| 这段文字是                                                                 | 怎么处理                                                               |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 指令，或模型必须读懂的一句话（说明、标题、提示、标记里的句子）             | 有 English 和简体中文两份，一句对一句，按会话的指令语言选一份          |
| 机器标记：XML 标签名、`[RUNTIME]` / `[retry N]` 这类方括号标签、枚举值、id | 不翻译                                                                 |
| 提示词正文按字面引用的文字                                                 | 不翻译；它是两种语言的正文共同引用的标记                               |
| 工具定义，以及工具循环里返回给模型的结果、拒绝原因和参数校验错误           | English。它们引用的字段名和枚举值来自 English 的工具定义，每种会话相同 |

框架代码用 `instructionLocaleFor(locale)` 选语言。现有的固定文字：

- `packages/context`：世界规则的标题 `[World Rule: …]` / `[世界规则：…]`，`<available-events>` 末尾的事件发射说明，历史摘要块后面的说明句，被裁掉的历史消息的占位标记，自有数据块为空时的 `(none)` / `（无）` 和条数说明，`characters.npcs` 里没有列出档案的角色名单。
- `packages/shared`：维度投影里“有几个维度未列出”的一行。
- `packages/runtime`：草稿被插件审查拒绝时的说明句，重试提示，工具结果和压缩历史被截断时的标记，`output.schema` runtime 的“只返回符合 JSON Schema 的 JSON”规则。最后一条由模型适配器加进 system prompt，所以每次模型请求带着会话的 `locale`。
- `packages/plugin-handlers-utils`：叙事审查（`createNarrativeReview`）加进请求的人称要求和三条纠错句，`characterSheetSegments` 的未列出档案名单。后者没有会话上下文，由调用方传入 `locale: ctx.locale`。

插件代码用自己已有的语言开关，没有的用 `pickLocaleText(ctx.locale, zh, en)`。hook 的上下文里没有 `locale`：往一次请求里加文字的 hook 读 system prompt 开头的框架前置段，它是中文时加中文（`char-creator` 的角色读取限制这样做）。内置插件里这样处理的有：`memory` 的提取提示词，`history-compaction` 的语言规则（它的模板有三种语言，规则也是三种），`world-init` 两个维度块的说明句和“已截断”标题，`story-events` 交给叙事的事件说明，`soundtrack` 的音乐情绪说明，`tabletop-rules` 的检定回执说明，`scene-stage` 的在场角色块，`branch-reply` 重生成候选的提示词。

两段文字因为被正文按字面引用而保持 English：`story-events` 在没有事件的回合给出的 `No hidden story event this turn.`，以及 `tabletop-rules` 回执开头的 `Settled tabletop check`。`narrator` 和 `chat-mode-narrator` 的两种语言正文都用这两段文字判断输入，改动它们等于改动 `story-event-cue@1` 和 `tabletop-check@1` 的输出。

`COVEL_INSTRUCTION_LOCALE` 只改变框架的选择。`pickLocaleText` 和插件自己的开关按会话 locale 判断，不读这个变量：强制 `en` 时，简体中文会话里由插件代码写的指令仍是中文。

新增一段由代码写进提示词的文字时，先判断它属于上表哪一类。框架源码里的中文行由 `pnpm check:i18n` 逐文件计数（`scripts/check-plugin-i18n.mjs` 的 `FRAMEWORK_CHINESE_LINES`），加了中文变体要同时改那张表。

### 语言分级

| 级别       | 语言              | 有什么                                                             |
| ---------- | ----------------- | ------------------------------------------------------------------ |
| `native`   | English、简体中文 | 界面、内置插件的标签与文字、内置世界的语言版本，以及模型读的指令。 |
| `extended` | 其他语言          | 界面，以及插件、世界自己提供的那部分文字。指令是 English。         |

`extended` 语言的会话让模型读 English 指令、用该语言写输出，故事质量取决于模型。语言选择器把这些语言标为“实验性”。级别由 `@covel/shared` 的 `localeTier()` 给出：它只看这种语言有没有自己的指令集，不是一张名单。繁体中文属于 `extended`：它读 English 指令，不读简体中文指令。

新增一种语言因此只需要一份界面 catalog 加上内容的语言版本，指令集不会变多。

## 会话语言在创建时锁定

一个会话有三种语言，各自只管一件事：

| 语言     | 何时确定                       | 决定什么                                         |
| -------- | ------------------------------ | ------------------------------------------------ |
| 界面语言 | 每次渲染，跟随玩家当前的设置   | 按钮、面板标题、插件名称等标签                   |
| 内容语言 | 创建会话时（`session.locale`） | 世界内容、模型写出的正文和数据、会话状态里的文本 |
| 指令语言 | 由内容语言推导，见上一节的规则 | 框架指令句与插件提示词用 English 还是简体中文    |

**内容语言必须是世界实际有的语言版本。** 创建会话时客户端传入玩家的界面语言；世界有这种语言的版本（`world.yaml` 的 `supportedLocales`），会话就用它；没有，会话用世界自己的语言（`defaultLocale`），界面仍是玩家的语言，客户端在进入前提示。这样不会出现“设定是一种语言、指令是第二种、却要求模型用第三种输出”的组合——小模型最先在这里出错。想用自己的语言玩一个没有该版本的世界，先用 `pnpm i18n translate` 给它补一个版本。

内容语言创建后不再改变。世界包里的多语言内容在导入会话时就解析成这一种语言，会话状态里只存普通字符串。`POST /api/actions` 不接受 `locale`，每个回合、手动 runtime 和后台任务都使用 `session.locale`。玩家在游玩中切换界面语言，只会改变标签，故事仍用原来的语言继续写。想用另一种语言游玩，需要新建会话。

AI 新建世界只生成请求内容语言的一份正文，`defaultLocale` 与 `supportedLocales` 分别固定为规范化请求 locale 和其单元素列表；要声明其他语言版本，必须另行生成对应译本。这条新建规范化不会裁掉修订世界已有的语言声明。

## 统一解析规则

所有框架和 Web UI 显示都必须通过 `@covel/shared` 的 `resolveI18nText(value, locale)` 解析，不得在组件内另写 `startsWith("en")`、`split("-")` 或 `Object.values()[0]` 式语言判断。解析顺序是：

1. 当前 locale 精确匹配，忽略大小写并兼容 `_` / `-`，例如 `en_US` 可匹配 `en-US`。
2. 当前主语言的短键，再尝试同语言、同 script 的其他区域键，例如 `en-US` 匹配 `en`；script 不同不会互相回退，例如 `zh-Hant` 不匹配 `zh` / `zh-CN`。
3. 按 locale registry 中声明的 `fallbackLocales` 依次回退；内置 registry 的最终 fallback 是 English。
4. 对象中第一个可用字符串。

没有传入 locale 时，为保持服务端和旧数据的确定性，直接取对象中第一个可用字符串。Web 组件应总是传当前 `i18n.language`。

`localeLanguage(locale)` 只负责提取主语言。资源候选必须使用 `localeLookupCandidates()`，同语言兼容性必须使用 `localesShareLanguageAndScript()` 或 registry 的 `match()`，不得仅凭主语言跨 script 折叠。

世界维度的值不在读取时翻译：`x-i18n` 节点在导入会话时就按会话的内容语言解析成普通字符串（`resolveWorldDimensionsLocale()`），会话状态里没有 locale map。其他仍带 locale map 的嵌套数据（例如面板标签）统一通过 `resolveI18nDeep(value, locale)` 解析。它只负责递归遍历数组和普通对象，保持输入的自有数据键，不把 `__proto__` 等 JSON 键解释为 JavaScript 原型操作；遇到 locale map 时仍委托 `resolveI18nText`，因此与 UI 使用完全相同的精确匹配、同语言匹配和英文回退规则。

## Web 边界

API 或插件 JSON 属于不可信输入。Web UI 通过 `apps/web/src/lib/i18n-text.ts` 的 `resolveDisplayText` 先丢弃非字符串字段，再调用共享 resolver，避免嵌套对象被当作 React child 渲染。已有的 `resolveI18n`、`text` 和 `textValue` 只是兼容入口，它们也必须委托到这条统一链路。

## 新增一种语言

以下以日语 `ja-JP`（文件变体可使用 exact `ja-JP` 或 script 兼容的短键 `ja`）为例。只翻译一个世界包时无需复制应用 catalog；要让玩家直接选择 `ja-JP`，只需随 Web/发行包加入完整 JSON catalog。

### 1. 注册应用语言

1. 运行 `pnpm i18n:add ja-JP` 生成完整模板，也可以手动复制 `apps/web/src/i18n/locales/en-US.json` 为 `apps/web/src/i18n/locales/ja-JP.json`。脚手架会按目标语言的 `Intl.PluralRules` 自动补齐 English 已标记 plural base 所需的 category。文件名必须是安全 canonical BCP 47 locale，且不能复用内置 code/alias（如 `zh`、`zh-Hans`、`en`、`ru`）；无需修改 `i18n/index.ts`、设置 schema 或切换器。
2. 只翻译 value，保持所有基础 key、JSON 类型、数组长度和 `{{ interpolation }}` token 不变。任何包含 `{{count}}` 的基础文案都可以增加目标语言需要的 i18next plural key，例如俄语的 `_few` / `_many`；脚手架生成的 category 只是 English 占位值，必须一并翻译。
3. 运行 `pnpm check:i18n`。检查器会校验文件名、内置 alias 冲突、与 `en-US` 的基础结构、English 已标记 plural base 的目标语言 categories、所有 plural variant 的插值变量以及代码实际使用的 key。
4. 运行 `pnpm --filter @covel/web test` 和 `pnpm --filter @covel/web build`。构建后 `ja-JP` 会自动出现在设置、首页顶栏和 Onboarding 中；`ja` / `ja-JP` 浏览器 locale 会自动匹配。
5. 可选：增加 `<name>.ja-JP.md` / `<name>.ja.md` framework prompt、`WORLD.ja-JP.md` / `WORLD.ja.md` 或 Electron 原生菜单翻译；缺少时按上文规则回退，不影响 Web UI catalog 生效。插件提示词不需要日语版本：日语会话读取 English 正文，并按会话 locale 输出日语。

无法立即翻译的框架内容必须明确回退到 English，而不是回退中文或改变稳定字段、枚举和业务契约。

### 2. 本地化插件

插件里的文本分为以下几类：

| 文本                                                                                                                            | 谁读                       | 写在哪                                                              | 支持的语言              |
| ------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------- | ----------------------- |
| 标签：`displayName`、`description`、命令和设置的 `label` / `description`、`title`、`summary`、作者信息的 `about` 和链接 `label` | 玩家，按界面语言           | 主清单写 English；译文在 `locales/<locale>.yaml`                    | 任意                    |
| 界面文字：UI spec（`ui/*.json`）里的面板名、按钮、提示，以及仅用于界面显示的徽标                                                | 玩家，按界面语言           | spec 和代码写 English；译文在 `locales/<locale>.yaml` 的 `messages` | 任意                    |
| 会话文字：handler、工具写入状态或模型上下文的提示和自然语言值                                                                   | 玩家和模型，按会话内容语言 | 代码写 English，经 `translate(ctx, ...)` 解析为一种语言             | 任意                    |
| 指令：提示词正文、`contributes.prompt` 固定段                                                                                   | 模型                       | 主文件写 English；简体中文在 `PLUGIN.zh.md` / `RUNTIME.zh.md`       | 只有 English 和简体中文 |

所以给插件加日语，只需要一个文件：

```text
plugins/dice-check/
├── PLUGIN.md              # English：契约、标签、提示词
├── PLUGIN.zh.md           # 简体中文提示词（可选；内置插件的 agent 必须有）
├── locales/
│   ├── zh.yaml            # 中文标签
│   └── ja.yaml            # 日语标签
└── runtimes/check/
    ├── RUNTIME.md
    └── RUNTIME.zh.md
```

`locales/ja.yaml` 按清单文件分节，每节只写译文，key 与主清单相同：

```yaml
PLUGIN.md:
  displayName: ダイス判定
  description: 危険を伴う行動を判定します。
  contributes:
    commands:
      - name: roll # 列表按 id / name / key 对齐
        description: ダイスを振る。
runtimes/check/RUNTIME.md:
  description: 危険な行動を一つ判定します。
messages: # UI spec 的文字：English 原文 → 译文
  Checks: 判定
  No checks yet.: まだ判定はありません。
```

加载器把这些译文编译成清单和 UI spec 上的 locale map，界面按玩家当前语言显示；没翻译的标签显示 English。日语会话读取 English 提示词并用日语输出，不需要、也不能提供日语提示词。

标签文件只能翻译上表列出的标签字段。它碰不到契约：写了 `runtime.type`、工具列表、提示词内容或主清单里没有的条目，这一条会被忽略并告警，`pnpm validate:plugin` 把它报为错误。主清单和 UI spec 里不再写内联 locale map（`displayName: { zh: …, en: … }`），校验同样会报错。

**代码里的文字**按会话内容语言逐条解析，使用与界面标签相同的共享规则：精确 locale → 同语言、同 script → English 原文。精确 locale 的词典不完整时，缺少的条目仍会查找同语言译文；不会因为存在一份局部词典就丢掉其他可用译文。

**代码里的文字**（handler、guard、工具、RPC 命令、扩展点处理函数写出的文字）同样只写 English，译文也放在 `messages` 里。宿主把译文作为 `ctx.messages` 交给代码，`@covel/plugin-handlers-utils` 提供两个读取它的函数：

```js
import { labelText, translate } from "@covel/plugin-handlers-utils";

// 会话语言的一份文字：给玩家的提示、放进提示词的标题、会被注入提示词的数据
translate(ctx, "World time: {display}", { display: clock.display });

// 插件带的每种语言各一份：只由界面绘制的徽标、状态名；界面按玩家的界面语言挑
labelText(ctx, "Critical success"); // { en: "Critical success", zh: "大成功" }
```

- 传入的 English 必须是常量字符串，变化的部分用 `{name}` 占位符加参数传入。校验器靠读源码找出“代码里已经没有的原文”，运行时拼出来的字符串它读不到，会直接报错。
- 会被注入提示词的数据（`io.selfData`）用 `translate`，不要用 `labelText`：后者含所有语言，模型会全部读到。
- 没有译文、或上下文里没有 `messages`（旧宿主、测试里手写的上下文）时，两个函数都返回 English 原文。
- 界面和代码用了同一句 English、译法却不同时，给界面那条加属性名前缀（`label|Completed: 已完成`），不带前缀的那条归代码（`Completed: 完成`）。
- `pickLocaleText(locale, zh, en)` 只用于代码写给模型的**指令**（例如骰子插件注入叙事提示词的判定规则，或一个提示段末尾的说明句；见[代码拼进提示词的文字](#代码拼进提示词的文字)）。指令和提示词正文一样，只有 English 和简体中文两种。
- 测试里用 `@covel/plugin-test-utils` 的 `loadPluginMessages(pluginRoot, locale)` 取得宿主会传入的 `ctx.messages`。

`messages` 以 English 原文为 key：原文改了，旧译文就不再匹配，界面回到 English，`pnpm validate:plugin` 把这条译文报为错误。同一句原文需要两种译法时在 key 前加属性名，如 `shortLabel|Codex`。规则详见 [UI 面板 · 插件 UI 文本规范](./ui-panels.md#插件-ui-文本规范)。

### 3. 本地化世界包

主文件只写一种语言。先在 `world.yaml` 声明默认语言和可用语言：

```yaml
defaultLocale: en-US
supportedLocales:
  - en-US
  - ja-JP
name: My World
summary: An example world.
```

再在每个要翻译的文件旁边加一份语言文件，只写译文：

```text
worlds/my-world/
├── world.yaml
├── world.ja.yaml          # name / summary / 属性名等标签的日语
├── WORLD.md
├── WORLD.ja.md            # 正文整份替换
├── characters/
│   ├── main-cast.json
│   └── main-cast.ja.json  # 按 id 对齐，只写翻译了的字段
└── data/
    ├── dimensions.yaml
    ├── dimensions.ja.yaml
    └── rules/
        ├── core.yaml
        └── core.ja.yaml
```

```yaml
# world.ja.yaml
name: 私の世界
summary: サンプル世界です。
```

`data/world.data.yaml` 只声明主文件，例如 `characters/main-cast.json`。创建 `ja-JP` 会话时，导入器把 `main-cast.ja-JP.json` 或 `main-cast.ja.json` 的译文合并到主文件上；没翻译的字段沿用主文件，结构、id 和数值始终来自主文件，所以可以逐步翻译，也不会因为复制整份文件而漂移。嵌套对象列表可在 source 中用 `localeArrayKeys` 声明稳定键（如 `label`），译文保留键后不受插入或排序影响；媒体哈希、路径等结构字段应只存在主文件。完整的合并规则见 [World Data](./world-data.md#语言文件namelocaleext)。

#### 插件没有某种语言时

缺一种语言不会阻止安装或启用，各层分别回退：

| 层                         | 插件没有这种语言时                                           |
| -------------------------- | ------------------------------------------------------------ |
| 标签与界面文字             | 同语言的其他地区，然后是包外翻译（见下），最后是 English。   |
| 代码写进状态和上下文的文字 | 同上。                                                       |
| 指令（提示词正文）         | 用插件有的那份：简体中文会话读 `*.zh.md`，其他都读 English。 |
| 游玩中模型生成的内容       | 不受影响，由框架的输出语言指令决定。                         |

插件有哪些语言由文件决定，不需要声明：`locales/<locale>.yaml` 增加一种文字语言，manifest 旁边的 `*.zh.md` 增加中文指令。这份摘要出现在三个地方：

- `pnpm validate:plugin <dir>` 的输出：`languages: text en, zh; instructions en, zh`；
- 插件列表接口的 `languages` 字段，会话准备页据此给没有当前界面语言文字的插件显示“未翻译”；
- `POST /api/sessions` 的响应：`pluginsWithoutLocale` 列出启用了、但没有会话语言文字的插件。会话照常创建。

#### 包外的翻译

译文也可以不在插件包里。**翻译目录**（`COVEL_USER_TRANSLATIONS_DIR`，默认 `$COVEL_HOME/translations`）里的 `plugins/<pluginId>/<locale>.yaml` 与插件自己的 `locales/<locale>.yaml` 格式完全相同：

```text
~/.covel/translations/
└── plugins/
    └── dice-check/
        └── ja.yaml
```

两种来源用同一个目录：

- **翻译包**：别人为若干插件做的译文，按上面的结构放进翻译目录即可。
- **本机机器翻译**：`pnpm i18n translate <plugin-dir> --locale ja --to ~/.covel/translations`，译文写进翻译目录而不是插件包。

优先级是：作者随插件发布的译文 → 翻译目录 → English。翻译目录只补作者没翻译的条目，同一条两边都有时用作者的。

翻译目录只放标签和 `messages`。**指令不从这里读**：没有人审过的指令译文等于没有人审过的行为改动，所以 `*.zh.md` 只认插件包里的那一份。翻译目录里的文字和世界包的文字属于同一类输入：标签会显示给玩家，`messages` 里的代码文字会进入模型上下文，因此只安装你信任的翻译包。

`messages` 以 English 原文为 key，插件更新后原文变了，旧译文自然不再匹配。标签按位置对应，翻译目录里没有 `lock.json`，插件改了某个标签的原文后旧译文会继续显示，重新运行 `translate --to` 或手工更新即可。服务端在启动时读取翻译目录，改动后需要重启。

### 4. 翻译工具

`pnpm i18n` 对一个插件目录（有 `PLUGIN.md`）或世界目录（有 `world.yaml`）工作：

```bash
pnpm i18n status plugins/dice-check                    # 每种语言翻译了多少
pnpm i18n status worlds/emberback --locale zh-CN --missing   # 逐条列出还缺什么
pnpm i18n extract plugins/dice-check --locale ja       # 打印一份待填写的 YAML
pnpm i18n translate worlds/emberback --locale zh-CN    # 用配置的模型补上缺的部分
pnpm i18n lock plugins/dice-check                      # 确认标签译文与现在的 English 对应
pnpm i18n translate plugins/dice-check --locale ja --to ~/.covel/translations   # 译文写到包外
```

| 命令        | 做什么                                                                                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`    | 统计每种语言的覆盖情况。插件分两项：标签（清单里的名称、说明）和 `messages`（界面与代码文字）；世界按文件列出。`--missing` 逐条列出缺的和过期的。                                                       |
| `extract`   | 把插件在某种语言里缺的条目打印成 YAML，值是 `TODO: <English>`，填好后合并进 `locales/<locale>.yaml`。                                                                                                   |
| `translate` | 请模型翻译缺失和过期的条目，写入语言文件。它和服务端一样读取 `llm.toml` 与环境里的 key；`--slot` 指定槽位，`--dry-run` 只列出要翻译的内容。每条译文都会检查占位符是否原样保留，不合格的重问一次后报告。 |
| `lock`      | 把插件每条标签译文“对应的 English 原文”记进 `locales/lock.json`。                                                                                                                                       |

**过期怎么判断。** `messages` 以 English 原文为 key，原文一改旧译文就不再匹配，自然显示为“缺失”，不需要记录。清单标签按位置对应（`displayName`、`contributes.commands[name=bag].description`），English 改了旧译文仍然“在位”，所以用 `locales/lock.json` 记下每条译文是照哪句 English 翻的；`status` 和 `pnpm check:i18n` 用它找出过期的译文。人工改完译文后运行 `pnpm i18n lock`，`translate` 写入后会自动更新。

**世界包里哪些算文字。** 世界数据没有标注“哪些字符串是文字”的 schema，工具按样子判断：中日韩文写成的世界里，含该文字的字符串算文字；其他语言写成的世界里，不在标识符字段（`id`、`type`、`kind`……）下、且含空格或以大写字母开头的字符串算文字。一个纯文本列表（规则的触发词 `keys`、别名 `aliases`）只要有一项是文字，就整列翻译。这是给译者的参考，不是门禁；写出的语言文件由 `pnpm validate:world` 校验（译文无处安放、改动了非文本的值都会报告）。 `world.yaml` 里的作者名（`author.name`）和许可证（`license`）是例外：它们在任何语言下都按原样显示，不算待翻译文本，在语言文件里给它们写译文会让清单校验失败。

维度文件是例外，它的 schema 说明了哪些是文字：维度的 `name`、`description`、`updateRule`，节点的 `title` 和 `x-enumLabels`，以及 schema 节点标了 `x-i18n: true` 的值。**没标 `x-i18n` 的值不会被本地化**，在任何语言的会话里都按原文出现；`status` 会报告“有多少个值读起来是文字却不能翻译”。要让地理、势力、历史这类叙述性的初始值能翻译，先给对应的 schema 节点加上 `x-i18n: true`。

**同一个名字只有一种译法。** `translate` 对相同的原文只翻译一次；翻译世界时先译名字（`name`、`title`、`aliases` 等字段里的短文本），再把译名作为术语表带进后续每一批；该语言已有的译文同样作为术语沿用，所以补翻一个不完整的版本时不会改掉已有的名字。

**在应用里翻译世界。** 世界没有玩家界面语言的版本时，世界详情页提供“翻译成〈语言〉”：确认后服务端执行与 `pnpm i18n translate` 相同的流程（`POST /api/worlds/:id/translate`），把语言文件写进世界包并登记到 `supportedLocales`。它只对用户世界目录里的世界包可用，并且先让玩家确认，因为要花模型调用。

**模型译文是草稿。** 人名地名、世界观术语和语气需要人看一遍。内置插件的中文由 `pnpm check:i18n` 强制齐全且不过期；世界包没有这条强制。

### 5. 校验

```bash
pnpm check:i18n
pnpm --filter @covel/shared test -- i18n
pnpm --filter @covel/plugin-world-init test
pnpm --filter @covel/web test -- i18n-text execution-timeline
```

还应实际切换到新 locale，检查设置页、世界选择页、会话创建、插件面板、Agent prompt 和 WorldData 导入结果。`pnpm check:i18n` 负责发现现有扫描范围内的裸 CJK 文案、缺少 English fallback 的 `I18nText`，以及任一 Web catalog 缺 key 的问题，但不会验证翻译质量。

## 插件示例

```yaml
id: dice-check
kind: plugin
displayName:
  zh: 骰子判定
  en: Dice Check
description:
  zh: 为有失败风险的行动提供骰子判定。
  en: Resolves risky actions with dice checks.
```

`id` 是稳定的插件 ID；插件列表、设置导航和执行时间线都显示经当前 locale 解析后的 `displayName`，只在缺失时回退到 `id`。
