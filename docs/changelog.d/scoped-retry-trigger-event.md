### Added

- **A write service knows which turn a retry repeats.** Its context carries `sourceTurnId` when the caller is a scoped retry of a committed turn, so a provider that books costs per turn can avoid settling the same transaction twice. `callTestService` accepts `caller.sourceTurnId` to test this. See [what a write service can access](../en/reference/plugin-extensions.md#what-a-write-service-can-access).

### Fixed

- **Retrying an event follower gives it the event the original turn gave it.** A runtime result now records `trigger: { topic, producerRunId }` for a synchronous event follower. A scoped retry of that runtime reads this field from the runtime's own result in the original turn, so a later attempt without the event does not lose it, and hands it the first payload of that topic from the same producer, if the producer succeeded; other runtimes do not run again and no event is emitted. Results saved before this change have no `trigger`, so their followers are retried without an event. See [limits of a batch recovery](../en/reference/api.md#limits-of-a-batch-recovery).
- **A retried runtime that failed can call write services again.** In a scoped retry, a selected runtime whose result in the original turn failed may stage write-service operations; every other runtime still gets `unavailable`. Retrying a rejected dice-check receipt now settles its cost once. A committed success in the source turn or a recovery is final: retrying a target that already succeeded is refused, and no later failure makes it retriable again, so it cannot charge twice. Only host-admitted recoveries (`retry_runtime` / `retry_failed_runtimes`, recorded as `retryScope.recovery: true`) count: a plugin RPC or job with `retryFromTurnId` gets neither the original event nor write services, so neither its success nor its failure ends or reopens the task. See [where write services cannot be called](../en/reference/plugin-extensions.md#where-write-services-cannot-be-called).
- **The inventory does not take a cost twice when a check is retried.** The ledger credits the losses it takes from the prose per story turn and item (`prose-losses`, key `<turnId>/<item>`), and `inventory.change@1` claims them first in a retry of that turn, reporting the removal as `skipped`. Both sides write `inc` operations, so the targets of one batch recovery can claim different items, or parts of one item's credit, in the same commit. Inventory is 0.0.48. See [built-in plugins · inventory](../en/builtin/rpg.md).

### Upgrade notes

- **Recoveries saved before this change no longer count.** Turn results written before `retryScope.recovery` existed carry no mark, so a task recovered in an existing development session shows as failed again and can be retried, and pay, once more. Recreate development sessions in which failed tasks were recovered.
