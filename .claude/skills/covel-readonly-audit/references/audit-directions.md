# 专项清单

本清单只定义每个专项审什么。授权和只读边界以 [SKILL.md](../SKILL.md) 为准：规划模式下，不要因为读了这份清单就去读项目源码。

下面出现的包名和目录只是找入口的线索，没有核实过它们现在是否还是这样。执行时从实际入口定位。

每个专项列出的契约文档，路径都相对于仓库根目录，不是相对于本 `references/` 目录，所以要先定位仓库根。文档只说明契约是什么；实际的代码路径通过 `docs/README.md` 的 Search Map 和调用关系来找。

## 总览

| 编号 | 专项 | 范围 |
| --- | --- | --- |
| A1 | 前端状态层 | `apps/web` 的 stores 和 services |
| A2 | 前端界面 | 组件、设置页、三份语言文件、主题 |
| A3 | 服务端 | `apps/server` 的路由、中间件、SSE |
| A4 | 存储 | 三个后端和 `DataStore` 契约；浏览器私有存储 |
| A5 | 模型网关 | `ai-provider` 的文本模型调用链，以及调用方的重试逻辑 |
| A6 | 插件开发体验 | 拆成两个子任务。A6a：加载器、公开 SDK、脚手架、校验脚本、作者指南。A6b：内置插件 |
| A7 | 世界包规范 | 世界校验、导入、四个内置世界、世界生成器 |
| A8 | 内核其余部分 | 工具循环、提交、函数运行时、钩子、内置工具 |
| A9 | 桌面端等 | Electron 壳、设置存储、记忆检索（关键词和向量）、事件总线 |
| A10 | 媒体管线 | 图像、语音、音乐的模型调用，媒体存储，媒体的引用和回收 |
| A11 | 挂起、恢复与后台作业 | 挂起和审批、恢复执行、后台作业队列、进程重启后的恢复、关闭流程 |
| A12 | 安装与信任边界 | 插件、世界和合集的安装、更新、卸载；社区插件授权；出站请求防护；桌面自动更新 |

A10 到 A12 各是一条跨层的链路。它们单独成为专项，是因为这些代码不属于任何一层的范围：没有专人负责时，每个专项都只会把它写成自己的缺口。

## 适用于所有专项的规则

- **五类分支**：每个审计目标都要检查正常、失败、取消、重入和释放；某一类不适用时写明原因。
- **测试**：已有的测试可以当作契约预期和反例线索来读，但不运行。
- **可枚举的对象**：审计目标针对一组可以枚举的对象时，先从代码和目录里列出实际清单，再按对象逐个给覆盖状态。各专项的“逐个核对”一行写明是哪些对象。清单本身不写在这里，因为它会随版本变化。
- **分工**：一段代码只有一个主责专项。专项说明里写了归另一个专项的内容，读到时把线索记进记录文件的“跨层边界和交给其他专项的线索”，不替对方下结论。

每个专项下面有四部分：**审计目标**是要逐条给出覆盖状态的检查项；**逐个核对**是要按对象列清单的集合；**取证要点**说明证据要追到哪里、哪些结论不能下；**契约文档**是执行时先读的入口。

## 所有专项都要查的仓库约定

仓库根目录 `AGENTS.md` 的 Critical Conventions 一节列出了全仓都要遵守的约定。这里不抄录，因为它会变。执行时读当前版本，把适用于本专项范围的每一条当作审计目标，结果填进“仓库约定符合表”。

下面几条最容易在专项的分界处漏掉。它们只是提示，以 `AGENTS.md` 的当前内容为准：

- 框架代码不按具体的插件 ID 或名称分支。A6b 查的是插件越界依赖框架；反过来的方向，要由读框架代码的各个专项来查。
- 写给模型看的文本不带簿记字段，例如会话 ID、行的 UUID、时间戳。
- 游戏随机数走插件上下文提供的随机源。
- 只保留当前契约：没有旧版本迁移、双读双写、别名，也没有专为兼容保留的分支。
- 展示字段按会话语言解析时，走统一的解析函数，不各写各的判断。

## A1 前端状态层

审计目标：

- 流式消息是否重复、遗漏或乱序。
- 重连和补偿是否一致。
- 中止是否释放连接，并挡住迟到的写入。
- 切换会话是否串数据。
- 订阅、消息、缓存和历史记录是否随长局无限增长。

逐个核对：订阅和缓存。

取证要点：核对事件的身份、顺序、去重键、会话归属和终态。追到订阅的创建和释放、异步回调、历史补偿各自的具体写入点。服务端发出了正确的事件，不能证明 store 消费得正确。浏览器私有存储的内部实现归 A4，本专项只查 store 怎么使用它。

契约文档：`docs/reference/protocol.md`、`docs/architecture/storage.md`

## A2 前端界面

审计目标：

- 加载、空、错误、中止四种状态是否完整，并且可以恢复。
- 设置在保存、失败和生效时的反馈是否一致。
- 翻译缺失、插值和硬编码文本。
- 键盘操作、焦点、可访问名称、对比度。
- 手机宽度下的溢出、遮挡和操作可达性。

逐个核对：语言文件的键、主题、设置页的各个面板。

取证要点：逐一核对三份语言文件的键、插值和调用处，确认主题和窄屏样式来自哪里。源码能证明缺少标签或缺少某个状态分支，证明不了真实设备上的焦点、对比度、遮挡和可达性；这几项列为待验证。

契约文档：`docs/reference/ui-panels.md`、`docs/reference/ui-components.md`、`docs/reference/i18n.md`、`docs/reference/settings-store.md`、`docs/reference/theme-packages.md`

## A3 服务端

审计目标：

- 输入校验和错误映射。
- 同一会话的并发，锁的范围和释放。
- 断连和任务取消之间的关系。
- SSE 的初始化、重放、心跳、关闭和资源回收。
- 认证、授权、密钥、路径和外部请求的安全边界。

逐个核对：路由，以及每把锁的获取者。

取证要点：找齐每把锁的获取者、持有范围和全部释放出口。区分 HTTP 断连、SSE 断连和执行取消。外部请求从参数来源追到校验和实际发出请求的实现；不通过真的发请求来验证边界。出站请求防护层自身的实现归 A12，本专项查服务端各处是否都经过它。恢复和后台作业的路由归 A11，安装路由归 A12，媒体路由归 A10。

契约文档：`docs/reference/api.md`、`docs/reference/protocol.md`、`docs/architecture/security.md`

## A4 存储

审计目标：

- 排序、分页、缺失值、更新、删除和唯一性的语义是否一致。
- 查询和索引是否匹配。
- 全表读取和 N+1。
- 事务原子性、并发更新、提交失败和回滚。
- 长局数据规模下的读写放大。
- 浏览器私有存储：检查点的写入、恢复和同步是否原子，恢复出来的状态是否完整。

逐个核对：`DataStore` 的方法。

取证要点：对同一个 `DataStore` 方法横向比较 MemoryStore、SqliteStore、PgStore，不要把三个后端各自孤立地读一遍。区分违反契约和契约允许的后端差异。有索引，不等于查询计划实际用到它。

浏览器私有存储（BrowserVault、IndexedDB、浏览器同步）不是第四种 `DataStore` 后端，不放进后端差异表。它按自己的检查点契约单独审：本专项读它的内部实现，H7 再把恢复路径连起来。向量存储的检索语义由 A9 主责，媒体存储由 A10 主责，本专项只提供存储层的证据。

契约文档：`docs/architecture/storage.md`、`docs/reference/transactions.md`

## A5 模型网关

审计目标：

- 缓存断点的位置和稳定性。
- 流式和非流式两种调用的用量统计。
- 失败、取消、重试时用量归到哪里。
- 多层重试是否放大成本。
- 首 token、空闲、单次调用、整体四种超时是否协调。
- 错误提示是否准确。

逐个核对：文本协议的 adapter。

取证要点：从调用方一路到网关和 provider adapter，列出每一层重试、最大尝试次数、取消如何传递、用量在哪里聚合。区分一次逻辑调用和它包含的多次物理尝试。静态算出的最坏次数只是已证实条件下的上界，不能折算成实际费用。图像、语音、音乐的调用归 A10，出站请求防护归 A12，本专项只管文本模型的调用链。

契约文档：`docs/reference/slots.md`、`docs/reference/prompt-structure.md`、`docs/architecture/flow.md`

## A6 插件开发体验

本专项拆成两个子任务，各有一个负责人和一个记录文件，编号分别用 A6a 和 A6b。只查插件和框架之间的契约，不评价各个插件的玩法设计。

契约文档（两个子任务共用）：`docs/guide/plugin-authoring.md`、`docs/reference/plugins.md`、`docs/reference/extension-points.md`、`docs/reference/plugin-extensions.md`、`docs/reference/plugin-installation.md`

### A6a 加载器与 SDK

范围：加载器、公开 SDK、脚手架、校验脚本、作者指南。

审计目标：

- 从作者声明到实际加载，契约是否一致。
- 静态校验和运行时注册之间是否有落差。
- 脚手架和文档是否匹配当前接口。
- 错误是否可以定位。

逐个核对：清单和运行时声明的字段。

取证要点：拿同一个字段一路追下去：作者声明、schema 和校验脚本、解析、编译、注册、消费方。A6b 报来的每一项越界依赖，由本子任务查公开 SDK 能不能表达这个需求。安装、更新和授权的流程归 A12。

### A6b 内置插件

范围：`plugins/` 下每一个现行的内置插件，不含 `_archive/`。

审计目标：

- 列出每个内置插件的越界依赖：依赖了什么、实际需要什么、缺少哪个公开 SDK 接口，并区分接口缺口和单纯的违规使用。
- 每个内置插件是否符合 `AGENTS.md` 的 Plugin authoring contract 一节。

逐个核对：内置插件。每个插件一行，没读过的写“未读”，不能只枚举名字就算覆盖。

取证要点：内置插件的每一项越界依赖，先查公开 SDK 能不能表达这个需求，再判定是接口缺口还是违规使用。只发现一处内部 import，不足以证明 SDK 缺少接口。

## A7 世界包规范

审计目标：

- 校验、导入、生成三处是否接受同一份契约。
- 引用、语言版本、种子数据、插件契约和媒体路径是否一致。
- 导入失败是否留下部分状态。
- 四个内置世界逐个、逐项检查。
- 生成器的输出是否满足校验和导入的要求。

逐个核对：内置世界，每个世界再按语言版本分行。

取证要点：四个内置世界每一个都要覆盖全部合规维度，不能用一个世界代表其余的。追踪生成器的输出 schema、写包规则和失败恢复。生成提示词提出了要求，不等于输出一定满足要求。校验器和生成器只读源码，不运行。ZIP 和 GitHub 的安装入口归 A12，媒体字节的写入和回收归 A10；本专项提供世界校验这一侧的证据。

契约文档：`docs/reference/world-data.md`、`docs/reference/world-model.md`、`docs/reference/world-installation.md`、`docs/reference/i18n.md`、`docs/reference/transactions.md`

## A8 内核其余部分

审计目标：

- 调度、权限、工具查找和执行上下文是否一致。
- 循环的终止、取消、超时和失败传播。
- proposal 从校验到提交的原子性。
- 函数超时之后迟到的副作用。
- 钩子的顺序和隔离。
- 内置工具定义的体积、重复内容和实际暴露范围。

逐个核对：proposal 类型及其处理器、钩子事件、内置工具。

取证要点：分清三组容易混淆的事：工具查找和工具授权；工具返回成功和 proposal 提交成功；函数的 promise 超时和底层工作真正停止。追到执行身份、事务边界，以及超时之后仍然能触达的副作用入口。挂起、恢复和后台作业归 A11。

契约文档：`docs/architecture/flow.md`、`docs/reference/tools.md`、`docs/reference/plugins.md`、`docs/reference/transactions.md`、`docs/reference/prompt-structure.md`

## A9 桌面端等

审计目标：

- IPC、窗口和导航的安全。
- 启动、退出和资源清理。
- 设置的持久化、同步、密钥保存和失败恢复。
- 记忆检索的过滤、排序、扫描规模和上下文占用。
- 向量：入库和索引是否与源数据一致；源数据删除或禁用之后，旧向量是否还能被检索到；embedding 调用的重试和用量；向量数据的回收。
- 事件订阅的释放、重放、背压、异常传播和跨会话隔离。

逐个核对：IPC 通道、检索来源（关键词和向量各算一个）。

取证要点：桌面、设置、记忆、向量、事件总线五个子域分别给出覆盖结论。每项资源都要找到创建者、释放者，以及它归属于哪个会话或窗口。配置里声明了隔离或过滤，不等于消费方完整地执行了它。关键词检索和向量检索要用同一套过滤条件对照。桌面自动更新归 A12。

契约文档：`docs/guide/desktop-config.md`、`docs/architecture/security.md`、`docs/reference/settings-store.md`、`docs/architecture/packages.md`、`docs/reference/protocol.md`

## A10 媒体管线

审计目标：

- 图像、语音、音乐的请求是否只路由到同类的模型槽位。
- 媒体调用的超时、重试、取消和用量归属。
- 字节写入、所有权登记和引用计数是否一致；调用失败、超时或取消之后，是否留下没人引用的媒体。
- 回收：会话删除、世界卸载等清理入口是否覆盖媒体的引用和字节；清理策略会不会删掉仍在使用的媒体。
- 各个媒体存储实现的语义是否一致。
- 媒体的访问控制：令牌的签发和校验，能否跨会话读取。
- 世界包里的媒体从导入到入库、建立索引的过程。
- 媒体数据随长局的增长。

逐个核对：各模态的 wire、媒体存储的实现。

取证要点：从插件调用媒体生成的入口，一路追到 wire、网关、媒体存储和前端展示。区分三个时点：字节已写入、所有权已登记、引用已建立，逐个查它们之间失败会留下什么。媒体存储有自己的契约，不并入 `DataStore` 的后端差异表。

契约文档：`docs/reference/image-generation.md`、`docs/reference/media-store.md`、`docs/reference/slots.md`、`docs/architecture/security.md`

## A11 挂起、恢复与后台作业

审计目标：

- 挂起时保存了什么；恢复后的执行是否沿用同一个执行身份、回合和插件注册视图。
- 审批通过、拒绝、超时、会话结束各自的结局；重复审批和重复恢复。
- 挂起之前缓冲的写入和恢复之后的写入，提交时是否原子。
- 过期挂起的清理。
- 后台作业的状态迁移：入队、认领、续租、执行、提交。同一个作业会不会执行两次，会不会永远到不了终态。
- 作业结果提交到已暂停、已结束、插件已移除或版本已变化的会话。
- 下一次执行之前等待后台作业的屏障。
- 进程中途退出后重启：停在提交中的回合、运行中的作业、挂起的执行、只存在于内存的锁和事件缓冲，各自由谁发现、怎么处置。
- 关闭流程：停止接收新请求、等待在途提交、超时后的处置。

逐个核对：挂起记录和作业记录的每个状态值，各自的写入者和读取者。

取证要点：区分三种“停下”：玩家取消、执行挂起、进程退出。挂起和作业都要找到持久化的那条记录。本专项能证明的是静态可见的恢复逻辑：重启后会运行哪段扫描代码、它覆盖哪些状态。进程真的被杀掉之后的行为只能列为待验证。

契约文档：`docs/architecture/flow.md`、`docs/reference/tools.md`、`docs/reference/api.md`、`docs/reference/protocol.md`、`docs/reference/transactions.md`、`docs/architecture/technical-debt.md`

## A12 安装与信任边界

审计目标：

- 安装包的处理：解包时对路径、大小和数量的限制。
- 安装、更新、卸载是否原子；失败后目录和数据库里是否留下残留。合集的整批安装和回滚。
- 安装入口的校验标准，是否与加载时和会话导入时一致。
- 社区插件在玩家授权之前，是否会执行任何服务端代码；授权撤销之后，已经注册的能力是否撤回。
- 插件声明的 HTTP 权限是否在所有出站路径上强制执行，校验失败时是否拒绝。
- 出站请求防护：对协议和主机的限制、DNS 固定、重定向的处理。
- 服务端和平台的密钥是否只发往可信的来源。
- 清单解析是否拒绝可执行的 frontmatter 指令。
- 桌面自动更新的来源、校验和失败恢复。

逐个核对：安装入口、出站请求的调用点。

取证要点：每个安装入口分别追，不拿一个入口代表其余的。对每条出站路径，找到它经过的防护函数；找不到就记为一条候选问题，不假定“应该都走了统一入口”。区分内置和社区两种来源，它们的信任级别不同。不发真实请求，也不安装真实的包来验证。

和相邻专项的分工：A6a 查作者契约，A7 查世界包的内容，A3 查服务端路由的认证和授权；本专项查包怎么进到机器上、进来之后被信任到什么程度。

契约文档：`docs/reference/plugin-installation.md`、`docs/reference/world-installation.md`、`docs/guide/collections.md`、`docs/architecture/security.md`、`docs/guide/desktop-packaging.md`
