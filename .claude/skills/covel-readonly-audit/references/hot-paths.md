# 跨层热路径

授权和只读边界以 [SKILL.md](../SKILL.md) 为准。规划模式只安排下面的顺序；执行模式等专项结果收齐后再通读。专项的证据是起点，边界两侧的实际实现和消费方仍然要读清楚。

每条热路径有一个记录文件，由汇总负责人写，骨架见 [报告约定](report-template.md)。读到的链路、证据和问题同样随读随记。

## 每个层间边界要回答的问题

每条热路径的记录里有两样东西：一条链路，每一环标出 `文件:行号` 和符号；一张边界表，回答下面的问题。专项里已经证明的片段引用同一个证据 ID，只补读还没读过的连接。

| 边界 | 必须回答 |
| --- | --- |
| 身份与视图 | 会话、执行、插件或 runtime、注册代际、语言，是否从生产方一直保留到消费方？中间发生映射时，由谁保证一致？ |
| 数据与顺序 | 生产方实际返回什么，消费方假定什么？校验、默认值、排序、去重和裁剪分别在哪一层做？ |
| 失败与取消 | 错误怎么映射？取消由谁传播，哪一层还在继续工作？重试覆盖的范围里有没有已经完成的副作用？ |
| 提交与终态 | 可见输出、持久化、广播、后续事件的先后顺序是什么？失败时谁决定终态，谁负责补偿？ |
| 中断与重启 | 进程在这一环之后退出，留下的是哪种中间状态？重启后由谁发现它，是继续、重做还是终结？ |
| 资源与规模 | 连接、任务、订阅、缓存或集合由谁创建、由谁释放？所有退出分支是否都走到释放逻辑？增长受什么上界控制？ |

每条路径都要读正常、失败、取消、重入和释放五类分支；静态条件确定不了的分支单独列为待验证。端到端链路缺了一段时，写明断在哪里，不能因为“相邻的模块都正常”就推定连接是安全的。

## H4 和 H7 的规模证据

- H4 要追到最终 provider 请求组装的地方，核对 system、history、current-turn、tool 四类消息，以及工具 schema、预留输出和 adapter 的重排。只读模板或预算入口是不够的。
- 每个体积来源分四类记录：静态常量、有条件的上界、按回合增长的量、未知量。字节数和字符数不能直接当作 token 数；源码里估算器的口径，不能当作供应商实际计费的口径。
- H7 从每回合新增的数据出发，追到下一次读取、恢复和组装，记下有没有窗口、分页、索引、截断、驱逐和清理。出现 `limit` 不代表有界：要查清 limit 是在读取之前生效，还是全量载入之后才截断。
- 复杂度结论要写明假设和变量，例如回合数、消息数、记录数和工具数。不能只凭源码就声称某个耗时、内存峰值、缓存命中率或费用已经发生。

## 共用证据与完成标准

同一个根因出现在多个专项或热路径时，只保留一个最终问题 ID；热路径为它补充证据、影响面和跨层根因。只有连接处引入了新的、独立的根因时，才把它另列为一个问题。

每条路径交付六项：链路、已覆盖的分支、发现的问题或“静态无发现”的说明、引用的问题 ID 和证据 ID、断点、待验证项。每条路径都交齐这六项，才算完成通读；有断点的路径保持“部分”或“阻塞”状态。
