# Covel 只读审计

只靠阅读，对整个 Covel 仓库做一次静态审计，交付一份每条结论都带代码位置的报告。审计分两部分，共用一套证据，最后合并成一份报告：

- **专项（编号 A1、A2……）**：每个专项通读一块代码，检查这一块自己的契约。多数专项对应一层，例如存储或服务端；少数对应一条跨层、但没有别的专项负责的链路，例如媒体管线。
- **热路径（编号 H1、H2……）**：每条热路径是一条穿过多层的链路，例如从前端输入到阶段调度。从头读到尾，检查层与层之间的连接。每一层单独看都正确、连起来却出错的问题，只有在这里才查得出来。

审计不改项目文件、不运行任何程序、不调用 Git、不调用项目的模型，唯一写入的地方是本次审计的报告目录。因此每条结论都是静态结论：它说明代码写了什么，不说明运行时发生了什么。

## 两种模式

- **规划模式（默认）**：只根据用户给的材料、仓库指令和本技能的文档，安排范围、分工、顺序和产出。不读项目的源码、配置和世界内容，不启动审计或子代理，不填写任何问题或合规结论，不写任何文件。给出计划后停下。
- **执行模式**：用户明确说“开始审计”或“执行审计”后才进入，并且只审用户授权的范围。加载本技能、创建本技能、要求做规划，都不算执行授权。

用户只要求部分专项或热路径时，列出没有覆盖的部分，不把局部结果称为全仓审计。审计做完就结束，不自动转成修复任务。

本技能只定义这一套审计流程。其他审计技能允许的做法在这里不适用，包括脚本验证和调用 Git。例如 `covel-static-turn-audit` 可以写探测脚本、运行 `git status`，本技能不可以。

## 只读边界

主代理和所有子代理都受下表约束。规划模式的限制更严，两者不一致时按规划模式执行。

| 事项 | 可以 | 不可以 |
| --- | --- | --- |
| 文件 | 读代码、配置、文档、测试源码和已有的静态材料；枚举目录、搜索文本、读取内容。在本次审计的报告目录里创建和补写计划、记录文件和最终报告。 | 创建、修改或删除报告目录之外的任何文件；往报告目录里放脚本、日志或截图。 |
| Git | 把用户给的 ref 当作未核验的标签记下来；通过读 `.gitignore` 确认报告目录被忽略。 | 任何 Git 命令，包括只读的 `status`、`diff`、`log`；创建 worktree、切换分支、提交。 |
| 执行 | 读应用、测试和脚本的源码。 | 运行应用、构建、安装、测试、lint、校验脚本或临时验证程序；操作浏览器；查询数据库；做性能采样。 |
| 模型与网络 | 审计代理自己的推理；经授权启动的子代理。 | 调用项目的模型网关、供应商 API、生成器或 embedding；用真实 LLM 做验证；发起业务网络请求。 |
| 敏感信息 | 优先读 schema、示例配置和处理密钥的代码；摘录证据时去掉敏感值。 | 为了审计去索取、加载或输出真实的密钥、令牌或玩家私有数据。 |
| 输出 | 把证据和报告写进报告目录；在对话里和子代理的结果消息里给出摘要和文件位置。 | 把报告写到报告目录之外；让问题只留在对话或上下文里，不写进记录文件。 |

除了报告目录，审计不在仓库和运行环境里留下任何改动，报告末尾的只读声明因此可以逐条核对。

## 随读随记

审计要读的代码远多于一次上下文记得住的量。全靠记忆、到最后才写，会漏掉问题，也会把位置写错。所以负责专项和热路径的代理（下面称负责人）都边读边写：

- 报告目录默认是仓库根目录下的 `devs/docs/audits/<日期>-readonly-audit/`，被 Git 忽略，不进版本历史。目录结构和每个文件的骨架见 [报告约定](references/report-template.md)。
- 每个专项、每条热路径各有一个记录文件，只由它的负责人写。并行的负责人共用同一份仓库，各写各的文件才不会互相覆盖。
- 读到能当证据的事实，或者发现一个候选问题，立刻写进记录文件，再继续往下读。路径和行号照着刚读到的内容写，不凭印象补。
- 记录只追加和补全，不删除。撤回的候选问题保留原编号，标为“已撤回”并写明原因。
- 最终报告由负责汇总的代理（下面称汇总负责人，通常是主代理）对着记录文件整理，不凭对话里的印象写。

## 静态证据能说明什么

报告里的每个判断归入三类之一，三类分开写：静态事实（代码、配置或文档直接写明）、推断（由事实推出，但还依赖没有证实的假设）、待验证项（只靠阅读得不出答案）。

- 测试源码说明预期，不说明测试通过。文档说明承诺，不说明实现已经做到。
- 没有运行过，就不能把行为、性能、实际 token 用量、缓存命中或费用写成已证实的结果。
- 文档和实现不一致时，记下差异和两边的位置。本次审计不修正文档。
- 需要运行才能确认的事项，只写验证方案，不执行。

## 流程

### 1. 确定范围，给出计划

读 [专项清单](references/audit-directions.md)、[热路径清单](references/hot-paths.md) 和 [报告约定](references/report-template.md)。这三份文档定义的是要审什么，不是已经核实过的当前代码事实。

计划里写明：当前是规划模式还是执行模式、专项的范围、热路径的顺序、并行批次、附表、报告目录的位置、证据的限制，以及没有覆盖的部分。不知道宿主能同时运行几个子代理时，只写“按可用并发数分批”，不编造并发能力。

计划里同时向用户确认三件事：

- **版本标签**：本技能不能调用 Git，所以请用户提供要审的提交号，例如用户自己运行 `git rev-parse HEAD` 的输出。它只作为未核验的标签记录；用户不提供时，报告里写明没有版本标签。
- **历史审计和已暂缓的问题**：用户希望参照哪些以前的审计报告，哪些问题已经决定暂缓。以前的报告通常在 `devs/audits/` 和 `devs/docs/audits/` 下。
- **报告目录**：在 worktree 里审计时，`devs/` 跟着 worktree 走，worktree 清理后报告会一起消失，所以请用户确认报告放在哪里。

**完成条件**：用户看得出要做什么、不做什么、做到什么程度算完成。规划模式到这里结束，不进入后面的步骤。

### 2. 建立只读基线，分配专项

获得执行授权后，先读仓库和相关目录的指令文件、对应的契约文档，再静态枚举实际的入口和被审对象。读文档是为了找到框架承诺了什么，不要把整套契约抄进报告。

**报告目录**：读 `.gitignore` 确认报告目录被忽略，没有被忽略就停下来问用户。然后创建目录，把计划和基线写成第一个文件，并为每个专项和每条热路径建好记录文件的骨架。

**基线**记录仓库路径、读取的起止时间、用户给的版本标签。起止时间取宿主提供的当前时间，取不到就写明没有采集。没有 Git 核验，所以不声称锁定了某个提交，也不声称工作区是干净的。读取期间文件发生变化、导致证据互相冲突时，把基线标为不稳定。

**对象清单**：凡是能枚举的被审对象，都先从代码和目录里列出实际清单，把数量记进基线，例如存储后端、界面语言文件、内置世界、内置插件、路由、proposal 类型、钩子事件。本技能提到的数量（三种存储后端、三份界面语言文件、四个内置世界）是预期值。对不上时，写明差异并按实际清单审计：不编造名称，不凑数，也不悄悄漏掉新增的对象。

**已知限制**：读 `docs/architecture/technical-debt.md`，它记录了有意保留的限制。用户指明的历史审计报告当作线索来读，每一条都对照当前代码重新核实，不照搬结论。已记录的限制和用户已决定暂缓的问题照常记录，但在“处置”一栏标出，不算新问题。

**分工**：每个专项一个负责人；专项清单里标明拆成子任务的专项，每个子任务一个负责人。按可用并发数分批、彼此独立地执行。交给每个负责人的任务只包含它那一个专项，并带上只读边界、随读随记的规则、它的记录文件路径、问题记录格式、它负责的附表和关联的热路径。每个负责人只写自己的记录文件，其余一律只读，也不为它们创建隔离的 worktree。

子代理怎么发现、是否需要用户授权、怎么编排，都按当前宿主的规则来。宿主满足不了只读、禁用 Git 或并发的要求时，向用户报告阻塞，由用户决定怎么调整，不自行换一种执行方式。子任务失败时，该专项不算已覆盖：如实报告，不盲目重跑，也不隐瞒；它已经写下的记录保留。

**完成条件**：报告目录和全部记录文件已经建好；每个专项都有负责人、范围和预期结果；没能启动的专项在记录文件里标为阻塞。开始读一个专项，不等于已经覆盖它。

### 3. 通读各专项

每个专项沿“实际入口 → 校验和转换 → 具体实现 → 消费方 → 清理”阅读，覆盖正常、失败、取消、重入和资源释放五类分支。关键词搜索只用来定位：单独的一处命中、一个函数名或一句注释，都不能代替调用链。

- 每读完一条调用链，更新记录文件里对应审计目标的覆盖状态：已通读、部分、未读或阻塞。
- 审计目标涉及可枚举的对象时，按对象逐个给覆盖状态。读不完时先读风险高的，并逐个写明读了哪些、没读哪些。抽样读的写成“部分”，不写成“已通读”。
- 每个候选问题一发现就记下来，随后补做反证检查：查上游的前置条件、下游的保护和清理分支，再写清触发条件在静态上是否可达。
- 每个候选问题都查现有测试：有没有测试覆盖这条路径；有的话，读它的夹具和断言，写明它为什么没有拦住这个问题。
- 并发问题写出可能的交错和涉及的共享状态。长局问题写出增长的来源、作用域、上界和清理入口。没有采样，就不声称竞态或性能退化已经发生。
- 核对仓库约定在本专项范围内是否成立，见专项清单的“所有专项都要查的仓库约定”。

负责人交回时，记录文件里要有：对象清单和覆盖状态、证据、候选问题、没有发现问题的目标的覆盖说明、待验证项、附表行、仓库约定的核对结果、需要在热路径里继续追踪的跨层边界，以及交给其他专项的线索。结果消息只给摘要和文件位置，不重复全文。

**完成条件**：专项清单里的每个目标都有覆盖状态；每个候选问题都有代码位置、确定性和反证检查。没有读过的目标，不能写成“未发现问题”。

### 4. 按顺序通读热路径

各批专项结果收齐后，汇总负责人先读全部专项记录文件，再按编号顺序追踪跨层连接。专项的证据直接复用，缺少的连接继续只读追踪，读到的内容同样随读随记。这一步不是把各专项的记录拼在一起，也不是把专项再做一遍。

在每个层间边界上逐项核对身份、数据形状、排序、错误、取消、提交时点、资源归属和重启后的恢复。新发现的跨层问题关联到相关专项。专项里已有的问题只补上 H 编号和新证据，不重复新增一条。

**完成条件**：每条热路径都有端到端的证据，或者写明断在哪里、为什么没有覆盖。前面的专项被阻塞时，依赖它的热路径只能报告部分覆盖。

### 5. 合并，交付

按 [报告约定](references/report-template.md) 合并问题：根因相同、触发链也相同的合成一条，并保留所有受影响的专项和热路径。症状相似但根因不同的，不强行合并。

问题按影响、触发条件和优先级排序。确定性单独列出：严重程度高，不能掩盖证据不足。已记录的技术债、已决定暂缓的问题和需要产品裁定的问题单独成组，不计入新增缺陷。确认全部附表都已返回。

最终报告写成报告目录里的 `README.md`。写完后对照记录文件核对一遍：每个候选问题要么进了最终问题，要么标了已撤回；报告引用的每个证据 ID 和代码位置都能在记录文件里找到。在对话里给出摘要和报告位置。

**完成条件**：报告约定“最终报告的结构”里的每个部分都齐全，包括按优先级排好的缺口清单和只读声明。只读声明逐项写明本次只写了报告目录、没有操作 Git、没有运行测试、没有调用项目的模型。缺少的部分标为“部分完成”，不补写没有证据的结论。

### 6. 补读缺口

仓库的规模决定了一轮往往读不完，结束时会有专项和热路径停在“部分”。最终报告里的缺口清单就是下一轮的任务单。补读需要用户再次授权，授权哪些条目就读哪些。

- 先读报告目录里上一轮的记录文件和最终报告。拿不到上一轮的文件时说明情况，不凭记忆续写。
- 只读被授权的缺口，不重做已经通读的部分，也不重新启动全部专项。
- 沿用原来的编号续编，新内容追加到原来的记录文件里并标明轮次。覆盖状态只在读完对应链段之后才提升。
- 更新 `README.md`，并在其中的轮次记录里写明这一轮的范围和变化。只读边界不变。
